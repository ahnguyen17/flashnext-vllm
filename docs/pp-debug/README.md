- GPU0/GPU1 = RTX 3090 24GB (sm_86); GPU2 = 170HX 64GB, GPU3 = 170HX 40GB (sm_80, cmpunlocker-unlocked, patched libcuda 610.43.03)

## The MTP hang — ROOT-CAUSED 8/30 ~01:00 (v24/v25 NCCL dumps)
- **v24/v25 verdict: NCCL ring participation deadlock, NOT a kernel/driver bug.** Watchdog dump (600s + `TORCH_NCCL_DUMP_ON_TIMEOUT=1`) named it: `BROADCAST SeqNum=1 NumelIn=4` on the `pp_broadcast` PG — ranks 0/1 "enqueued: 2, started: -1" (blocked synchronously inside `PPHandler.receive()` in `sample_tokens`), rank 2 never joined (walked past to its next `execute_model` irecv). GPU-util triangulation matches: waiting ranks 100% SM (NCCL spin), skipping rank 0%.
- **Root cause**: `compute_need_sampled_mask(input_batch)` gates ring participation on BOTH sides but reads rank-local, pipeline-lagged state (`num_computed_tokens_np`) → last rank's `broadcast()` early-returns while early ranks block in the matching recv. Spec-only because MTP changes the ring/p2p interleaving. v10's lone 301.8s success = the one run where masks happened to agree.
- **Fix lineage**: `pp3fix9` = +site-17 (ring on MAIN stream — kills the side-stream/sibling-communicator hazard; necessary, insufficient alone — v25 still hung identically) → `pp3fix10` = +**site-18: unconditional ring participation** (receive() always enqueues with mask as data filter — zeros array when None; broadcast() always sends, padding the token tensor to `max_sample_len` with -1 which consumers already filter) + site-15 (pure-torch post_update, bit-exact gated). **Lesson: collective rings must be unconditionally symmetric; filter semantics per-rank, never participation.**

## The method (generalizable)
1. **A constant success time just under a failure time = timeout race, not deadlock.** Find the constant's source in code (`grep -rn` the error string → walk up to the timeout param → envs.py). v10's 301.8s warmup vs 300s default RPC timeout was the key everyone missed for 14 builds.
2. **Read the raise site's source before theorizing.** `docker run --rm --entrypoint bash IMG -c "sed -n …"` — 30 seconds beats an hour of speculation.
3. **One variable per build.** A/B against the last known-good image. Log what changed.
4. **Suspect your own patches first.** Sites 11/12 "fixed" symptoms and regressed the path (1-token finalization). Reverting is a valid experiment — v18 proved the disease survived without them, exonerating them for the hang while convicting them for the regression.
5. **Frozen-line detection**: 3 py-spy dumps 20s apart, same line = livelock; moving lines = slow progress. `--native` for C frames (driver spin vs file-lock spin vs compile).
6. **Ground truth over HTTP status**: `curl /metrics` (`generation_tokens_total`) — v17's "200 OK" requests were client-disconnect artifacts, 1 real token between them.
7. **Isolation probes**: reproduce the load standalone (~/probe13.py pattern), then add context elements one at a time until it breaks.
8. **Unbuffered watchers**: `python3 -u`, tee to a file, abort conditions that auto-py-spy. Background-process stdout can buffer invisibly for an hour.
9. **The hang frame is where the WAITING is, not the DISEASE.** Any op after enqueued GPU work can "hang" — module loads, `.item()`, boolean-mask indexing (all implicit syncs). Decisive test: replace the suspected function with a pure-torch version; if the hang MOVES to the new function's first sync, the disease is upstream in the forward (v21's pivot).
10. **Env archaeology**: diff every env your scaffold forces against the fork's `envs.py` defaults. Fossil overrides from dead experiments survive nights of debugging — `VLLM_GDN_DECODE_KERNEL=triton` cost ~10 builds before anyone asked what the default was.
11. **Equivalence-gate kernel ports**: before burning a boot window on a triton→torch port, run bit-exact tests of both paths on identical inputs. Build ONE input set and `clone()` per arm — consecutive `make()` calls advance the RNG stream and fake a mismatch.
12. **State a build budget, renegotiate explicitly.** The user tracks boot costs ("how many more builds do we have to do?") — frame each phase as "1 decisive, at most N", and say plainly when evidence demands another. Don't silently exceed, don't silently stop.
13. **When every kernel probe passes but the engine hangs, stop probing kernels — arm the NCCL watchdog.** 600s distributed timeouts + `TORCH_NCCL_DUMP_ON_TIMEOUT=1` converts an infinite hang into an abort that names the collective, the PG, per-rank enqueue/start/complete counts, AND the python stack of the enqueue site. This single technique found what ~15 boots of kernel-chasing couldn't.
14. **Reference-implementation substitution settles implementation-vs-integration in one boot.** Suspect your port? Route the path through the stock kernel under conditions where it loads (e.g., tensor-variant instead of the deadlocking None-variant + dummy buffer). Same symptom with reference code = the bug is in the integration/cadence, not your code.
15. **Equivalence tests must cover EVERY branch — especially None/default arms.** Site-15's port was "bit-exact verified" on inputs that always supplied `query_start_loc`; the production path passes None, where the kernel still applies `-num_rejected` and the port skipped it. Enumerate the kernel's None/early-return branches and test each explicitly.
16. **Corruption signatures localize double-appends:** token-doubled echo ("capital capital! of of!") = the same tokens appended twice to context; prompt-doubled echo = prefill re-appended; correct-then-garbage = bookkeeping drift (num_computed/total_len divergence). Check `/metrics` spec counters (`num_drafts`, `num_accepted`) for the drafter's health separately from text quality.
13. **Confirm lane usage before auto-restoring prod.** Default instinct is to restore 8012 at every window close — the user corrected this: if he's not consuming the lane, he wants the debug window held open until the bug is fixed. Ask, don't assume.
17. **Quality-gate the baseline before localizing anything.** v20's 57 t/s "working" number had been banked for a day and never had its TEXT read — the ladder measured speed only. Reading it (clean) is what licensed blaming the spec path alone; had it been garbage, the whole debugging frame shifts. A baseline that's never been quality-checked cannot localize.
18. **Trace the counters before theorizing — the v30 lesson.** Three A/B builds (v27/v28/v29) could only bisect WHERE corruption lived; ONE boot with 6 print statements at the accounting points (scheduler `_update_after_schedule`: nct/sched/nts/ph; `update_from_output` spec branch: gen/draft/acc/rej/nct; ring consume: slot=data?) found the exact arithmetic. Static reading of placeholder/rollback algebra across async-scheduled PP has too many mutators — three self-consistent-but-wrong stories preceded the trace. Counter-accounting suspect in unfamiliar fork code ⇒ instrument first, argue after.
19. **Guard conditions must match the failure's true scope — find the sentinel in the data.** "First decode step" (v31) was the wrong discriminator: the leak recurred at step 7 because the drafter proposes nothing on ANY n-gram miss. The robust discriminator was intrinsic: placeholder ids are -1, real drafts are ≥0. When a guard keeps missing cases, stop enumerating instances and look for the invariant already encoded in the data.
20. **A correctness fix can silently kill the feature it guards.** Site-22 made the accounting airtight (clean text) but starved the drafter — zero drafts engaged all run, MTP inert at ~36 t/s vs 57 no-MTP — because the speculator proposes FROM scheduled slots. After any spec-path correctness fix, check engagement (SPEC-OUT count / drafts>0), not just cleanliness.
21. **Read files from a non-running image without a boot window:** `CID=$(docker create IMG) && docker cp $CID:/path ./ && docker rm $CID`. Used to extract spec-path sources from pp3fix12 while the running container sat on an older image, and to stage trace-patched trees before `docker commit`.
22. **Per-step accounting state in async-scheduled engines lives on the step's SchedulerOutput, never on the Request.** Async scheduling runs schedule(N+1) BEFORE update_from_output(N) — any request-side flag set by step N's schedule is overwritten by step N+1's schedule before step N's output processing reads it (v33: a correct phantom-rollback design silently no-op'd every step this way; the trace showed the leak persisting with zero PHANTOM lines). Dataclasses make this cheap: add an optional `dict[str, int] | None = None` field, populate in schedule(), read in update_from_output — the output object travels with its own step, race-free by construction. Corollary: when a fix that SHOULD fire doesn't, suspect state lifetime before logic — grep for every writer of the flag, not just the reader.
23. **Silent getattr defaults are guard-killers.** `getattr(self, "num_spec_tokens", 0)` on a V2 runner whose attr is actually `num_speculative_steps` returns 0 without error — and `corr <= 0` then disables the entire correction. When a guard depends on an attribute you haven't verified on the live class, grep the class FIRST (one line), or assert the attr exists so the failure is loud.
24. **Roll back the SAME ledger the optimistic write touched — counters are not interchangeable.** v35 crashed on `assert num_output_placeholders >= 0`: the phantom slots had inflated `num_new_tokens` via `num_tokens_with_spec` (the spec ids), NOT via the async placeholder reservation, so decrementing ph "for symmetry" underflowed it. Before any rollback, trace which writer added the optimistic count and reverse exactly that path. Corollary discovery: adaptive verification compacts the worker's schedule to 1+drafts, so the worker never leaks on phantom steps — the scheduler was the ONLY leaking side (a whole worker-side patch turned out to be a no-op safety net, `S24 rej0=0` proved it).
25. **Sentinel values may be load-bearing BY DESIGN — sanitizing them kills the feature.** The `[-1]` draft ids in `scheduled_spec_decode_tokens` looked like an obvious bug (garbage tokens into the model) and v35/v36 "fixed" them by withholding → engine crash then total garbage + zero engagement. They are SLOT MARKERS the in-forward drafter is supposed to fill; the actual bug is that nothing fills them. Before sanitizing a sentinel, find its consumer and confirm nobody was supposed to replace it downstream.
26. **Print the DATA VALUES, not just the counters.** v37's decisive line was `ids=[-1,-1,-1]` appended to the SPEC-OUT trace — one field showing the actual scheduled draft ids settled in one boot what three structural A/B builds (v33/v34/v35) couldn't: whether the pipeline ever replaces markers with real proposals. Counter traces localize WHERE; value traces settle WHAT. When two mechanisms could both explain the symptom, instrument the discriminating datum.
27. **Async trace lines don't map 1:1 to steps — mind the lag shift.** `OUT step=7` may be processing the batch SCHEDULED at step 4 (schedule N+1 runs while step N executes). Reading output-processing lines as same-step events produces plausible-but-wrong accounting stories; when the arithmetic "doesn't close", try re-aligning every output/spec line to the schedule line pp_size steps earlier before concluding a leak.

## Pitfalls (paid for in blood)
- `docker commit` bakes the run-time entrypoint — always `docker commit --change 'ENTRYPOINT ["vllm"]'`
- **Stacked patches collide on anchors**: site-21's insertion anchored on the same line site-20 had just grown a sibling under — the build died on IndentationError. Always `ast.parse` (or equivalent) inside the patch script AND `docker exec` a second parse of the final file before commit; the second gate caught nothing the first didn't, but the run-abort saved a broken image from being tagged.
- `docker exec … <<'EOF'` heredocs can swallow silently — write script to host, `docker cp`, exec the file
- `sed` on multiline flags fails silently (v20 launched WITH the flag I "removed") — verify with `grep -c`, or use the patch tool
- `pkill -f` self-matches your own shell — kill by port-derived PID (`ss -tlnp | grep :PORT`)
- Never `| head` a running script's output — SIGPIPE kills it mid-run
- 8012 watchdog cron (`8012-nightly-watchdog`) must be paused BEFORE taking prod down, resumed after (`cronjob pause/resume 5776c61d67ad`)
- Prod restore: `~/scripts/serve-flashnext-8012.sh` background, ~165s to healthy; AWQ GGUF untouched on disk
- Interrupted-mid-command turns (user interrupt during `kill && launch` chains): state can be half-changed — verify port/container/GPU state before assuming either half completed
