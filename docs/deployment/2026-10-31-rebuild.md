# 2026-10-31 — Full stack rebuild after image loss (MTP-3 + prefix cache restored)

The prod Docker image (the `pp3fix*` lineage, ~54 iterations) was destroyed in a
disk-space prune. The launch scripts survived; the image did not — and the image
*was* the recipe. This documents the rebuild that restored full prod numbers,
so it never takes a debugging campaign again.

## Results (measured, beats the original published lane)

- **Decode: 90–95 t/s** single-stream (original: 77–86)
- **Prefill: 4,231 t/s** @24K-token prompt (original: ~4,494)
- **4-concurrent: 70–75 t/s per stream** (~290 aggregate)
- 262,144-token native context, prefix caching ON, MTP-3 speculative decoding

## The image

Tag `rebuild-mtp-compile`. Build with `Dockerfile.rebuild` from the repo root
(requires the patch stack below). Key settings:

- Base: `vllm/vllm-openai:nightly`, checked out to **PR-53899 @
  `a5530b90cab09b187463396a99612a486ba91d6f`** (fetch by full SHA — the PR was
  force-pushed past this commit).
- **Full source compile**: `TORCH_CUDA_ARCH_LIST="8.0 8.6" pip install -e .
  --no-build-isolation` (~50 min on a 14-core Xeon). Do NOT use
  `VLLM_USE_PRECOMPILED=1` — the nightly's prebuilt `_C` ops predate the PR's
  Python call signatures (`gptq_marlin_repack` 6-vs-5 args) and the mismatch
  only surfaces at weight-load time on the AWQ rank.
- **`flashinfer-python==0.7.2.post1` pinned after the vllm install** — the
  resolver otherwise lands on a python/cubin version split that crashes any
  MTP config at model inspection ("failed to be inspected"), while no-MTP
  boots silently succeed.

## Patch stack (apply order matters)

1. `patches/rebuild/patch_pp.py` — PLE offload + PP-aware MTP fixes (PR tree)
2. `patches/site{13,15,17,18,19,20,21,26,27,28,31}.py` — the
   original site patches (site 27d already covers the mamba-align state fix)
3. `patches/rebuild/site32-pp-warmup-gate.py` — env-gated warmup skip at PP>1
   unless `VLLM_PP_WARMUP=1` (reconstruction of the original site-30 gate)
4. `patches/rebuild/site33-ple-worker-partition.py` — the PLE offload worker
   runs in its own world-1 group and must NOT inherit
   `VLLM_PP_LAYER_PARTITION` (crashes `get_pp_indices` under MTP configs)
5. `patches/rebuild/site34-marlin-repack-compat.py` — shim for prebuilt-_C
   images only; harmless after full compile
6. `patches/rebuild/mamba_align_port.py` — fallback port of the mamba-align
   scheduler hunk (site 27d usually already covers the second hunk)

Site 30 is a no-op in this tree (its anchors were the site-9/10 warmup skips,
which site-32 reconstructs).

## Operations (the part that is procedure, not code)

- **Boot takes ~13 min** (3 ranks + PLE worker + CUDA graphs).
- **Never send real traffic to a cold boot.** The boot battery
  (`scripts/boot-battery-warmup.sh`, a docker-events daemon) fires a
  tiny→medium→sustain→tiny2 sequence at every container start so first-use
  kernel loads happen on shallow traffic. First deep request on a cold engine
  wedges it (documented in `docs/pp-debug/references/mtp-hang-forensics.md`).
- First battery on a fresh triton cache costs minutes (JIT); the
  `vllm-triton-cache` volume persists across containers, so it is once per
  cache key.
- If `--prefix-match-unit` is used and boot fails with "group block sizes must
  be divisible": KV group layout can resolve to 1600 or 1568 depending on
  boot; 400 divides 1600 but not 1568. Drop the flag or align it.

## Restore from backup (fast path)

The compiled image is archived (docker save) at
`/mnt/st8/flashnext-image-rebuild-mtp-compile.tar.gz` on the serving host:

```bash
docker load < /mnt/st8/flashnext-image-rebuild-mtp-compile.tar.gz
docker rm -f qwen38-prod-8012 2>/dev/null
bash scripts/serve-vllm-pp3-262k-mtp-rank-reorder.sh   # + local API key env
```

Rebuild from scratch: `docker build -t qwen38-flash-next:rebuild-mtp-compile
-f Dockerfile.rebuild .` with the patch stack in `patches/`.

## Lessons

- The image is a build artifact of a debugging campaign; **archive it with the
  weights** at every lane cutover, or the campaign must be re-run.
- `VLLM_USE_PRECOMPILED` is only safe when the base nightly is the PR's own
  fork point. Otherwise compile.
- Silent env inheritance across vLLM's helper processes (PLE worker) is a
  real failure class; scrub rank-specific env at process entry.
